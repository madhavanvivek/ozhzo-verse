# Ozhzo Verse — Phase 3B: Shopping Requirements & Functional Specification

## 1. Functional Requirements

### 1.1 List Management
- **FR-SHOP-01**: Each Home possesses a default primary shopping list, with support for additional custom lists (e.g. "Weekly Groceries", "Hardware Store", "Party Supplies").
- **FR-SHOP-02**: All Home members can view and collaborate on the list in real-time.

### 1.2 Shopping Items & Origin Sources
- **FR-ITEM-01**: A shopping item must capture: `id`, `home_id`, `list_id`, `inventory_item_id` (optional), `name`, `quantity`, `unit`, `priority`, `source`, `status`, `added_by`, `assigned_to`, `notes`, `expected_price`, and `actual_price`.
- **FR-ITEM-02**: Supported Sources:
  - `MANUAL`: Added directly by a family member.
  - `LOW_STOCK`: Generated by inventory low stock detection.
  - `OUT_OF_STOCK`: Generated when an inventory item hits zero quantity.
  - `RECURRING`: Generated from scheduled recurring supply needs.
  - `RECOMMENDED`: Future AI/Predictive restock recommendation.
- **FR-ITEM-03**: Priority must support `LOW`, `NORMAL`, `HIGH`.

### 1.3 State Machine & Lifecycle
- **FR-STATE-01**: Item States:
  - `SUGGESTED`: Generated by system; pending member approval.
  - `ADDED`: Active on the shopping list.
  - `IN_CART`: Placed into physical shopping cart while shopping.
  - `PURCHASED`: Completed checkout.
  - `CANCELLED`: Dismissed or rejected from list.

### 1.4 Auto-Replenishment & Inventory Integration
- **FR-REPLEN-01**: Backend must compute suggested replenishment quantity based on:
  $$\text{Suggested Quantity} = \max\left(1.0, \text{preferred\_quantity} - \text{current\_quantity}\right)$$
  If `preferred_quantity` is null:
  $$\text{Suggested Quantity} = \max\left(1.0, (\text{min\_threshold} \times 2) - \text{current\_quantity}\right)$$
- **FR-REPLEN-02**: Purchasing an inventory-linked item must provide a restock confirmation prompt: *"Add purchased quantity to Home inventory?"*.
- **FR-REPLEN-03**: When confirmed, the system must execute an atomic database transaction that:
  1. Increments `inventory_items.quantity` by the purchased quantity.
  2. Updates `inventory_items.status` to `GOOD`.
  3. Appends a record to `stock_movements` with `movement_type = 'PURCHASE'`.
  4. Appends a record to `purchase_records`.

### 1.5 Shopping Mode (Mobile-First UX)
- **FR-MODE-01**: The mobile app must feature a dedicated "Shopping Mode" optimized for in-store use:
  - High-contrast, large touch targets (minimum $48\times 48\text{dp}$).
  - Grouping by category or store aisle.
  - 1-tap item check-off.

### 1.6 Purchase History & Price Tracking
- **FR-HIST-01**: Completed purchases are retained in an immutable `purchase_records` ledger.
- **FR-HIST-02**: Prices must use high-precision decimals (`NUMERIC(10, 2)`) to eliminate floating-point rounding issues.

---

## 2. Non-Functional Requirements

### 2.1 Concurrency & Duplicate Prevention
- **NFR-CONC-01**: Optimistic locking via integer `version` columns prevents race conditions when multiple members shop simultaneously.
- **NFR-CONC-02**: Checking off an item already marked as purchased by another member returns HTTP 409 Conflict.

### 2.2 Security & Tenant Isolation
- **NFR-SEC-01**: Every shopping route enforces `require_home_permission(...)`. Non-members receive HTTP 403 Forbidden.
- **NFR-SEC-02**: Unverified mobile accounts cannot create, edit, or purchase shopping items.

### 2.3 Performance & Indexing
- **NFR-PERF-01**: Shopping list retrieval must return in $< 30\text{ms}$ at p95 for lists with up to 500 items.
- **NFR-PERF-02**: Composite indexes must optimize `(home_id, list_id, status)` and `(home_id, purchased_at DESC)`.
